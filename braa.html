Bounded-Risk Agility Architecture (BRAA)

An Engineering and Cyber-Safety Architecture

for Fault-Tolerant, Measurable Autonomous Intelligent Systems

License: CC-BY-4.0
Year: 2026

1. Executive Summary

BRAA is an engineering and cyber-safety framework for autonomous intelligent systems operating under residual risk. Absolute determinism in stochastic Cognitive Cores is mathematically and empirically unattainable. The objective of BRAA is to keep residual operational risk bounded, measurable, observable, and economically controllable — not to promise its complete elimination.

The architecture is strictly Cognitive-Core-agnostic and infrastructure-agnostic. It treats the underlying inference engines (LLMs, VLMs, agentic loops) as untrusted, replaceable, and volatile components. It places all critical invariants, safety boundaries, and transition rules into a deterministic, immutable runtime environment (the Immutable Core) executed completely outside any prompt space or learned representation.

BRAA supports progressive adoption: organizations may begin with Profile BETA or GAMMA and migrate to Profile ALPHA as operational maturity and empirical calibration evidence accumulate. Within Profile ALPHA, depth of ensemble and verification mechanisms may be modulated according to observed risk stability and calibration quality, provided all mandatory invariants remain enforced.

2. Document Status & Compliance Framework

This document operates as a Technical Preprint. It is designed to guide system architects, cybersecurity engineers, and compliance auditors. It defines structural invariants and interface obligations (“what must be enforced and verified”) while remaining technology-neutral regarding the physical implementation layer (e.g., programming languages, specific databases, or cloud providers).

When implemented within an enterprise environment, this standard mandates strict adherence to the chosen Compliance Profile (Section 6). Compliance cannot be claimed unless the deployed system can programmatically validate the schema contracts defined in Appendix A and reproduce the mandatory verification criteria logged in Appendix C.

3. Terminology

  • Cognitive Core — The replaceable, stochastic inference engine or neural network driving autonomous decision-making.
  • Immutable Core — The deterministic, compiled module holding protective constants, hard transition rules, and cryptographic validation gates. It contains no learned parameters and cannot be modified via prompt injection.
  • Shadow Reference — A stable, historically validated system state used as a safe fallback for instant rollback execution.
  • Anchor Dataset — A versioned, cryptographically signed set of historical benchmark tasks and baseline reference vectors used to detect system drift and calibrate risk metrics.
  • Competence-Trace Vector (CTV) — An append-only, immutable record of long-term capabilities, including a non-linear rate-of-change drift signal.
  • Execution Trace Vector (ETV) — A compact, cryptographic micro-step record capturing the call-graph hash, code coverage, allocated memory, execution substrate, and hardware partition.
  • Risk Subscore Vector — A structured record containing precisely four independently computed components of risk: Uncertainty, Irreversibility, Blast Radius, and Novelty.
  • Loss Matrix — A versioned, governance-controlled aggregation function mapping the Risk Subscore Vector to a composite scalar value (risk_score).
  • Diversification Certificate — A time-stamped, periodically renewed cryptographic attestation measuring the decision-output disagreement rate of an ensemble against a standing adversarial holdout set. Disagreement is measured at the decision-output level (post-aggregation), not solely at token level, to avoid conflating stylistic divergence with substantive correctness divergence.
  • Honeytask — An unannounced, indistinguishable-from-real probe task injected into the execution stream to continuously verify the integrity of components operating under sampled review.
  • Resource Envelope — A machine-readable, strictly bounded budget contract limiting memory, compute tokens, API credits, and execution time.
  • State Contract — A schema-defined, bi-directional interface restricting data mutations and system transitions between isolated modules.
  • Adaptive Load Shedding — A risk-driven operational defense mechanism that drops or queues low-priority, high-risk work when the system undergoes infrastructure or verification pressure.
  • Hard Freeze — An automated state locking mechanism that completely halts self-improvement capabilities and rolls back the system to its Shadow Reference state.
  • Hardware Partition — A homogeneous compute node or group of nodes with matching, verified container image and configuration hashes.
  • SASG (Static Analysis Safety Gate) — A pattern-based, deterministic static analysis pipeline executing inside the Immutable Core.

4. Threat Model & Scope Limitations

Addressed Threats

  • T1: Prompt Injection (Direct & Indirect) — Unauthorized execution of malicious instructions embedded in user inputs or third-party data fetches.
  • T2: Hallucination Propagation — Unchecked compounding of false or corrupted state values through downstream tasks.
  • T3: Capability Drift — Gradual, silent degradation or unexpected shifts in the Cognitive Core’s behavior due to continuous updates or continuous context window filling.
  • T4: Split-Brain Inconsistency — Conflicting state updates across distributed or uncoordinated autonomous agents.
  • T5: Metric Gaming / Goodhart’s Law — Exploitation of reward functions or validation proxy metrics by the Cognitive Core during autonomous operations.
  • T6: Correlated Ensemble Failures — Simultaneous, identical failures across multiple models due to shared pre-training biases or structural blind spots.
  • T7: Storage-Pressure Timeouts — Resource exhaustion attacks designed to force the system into unsafe fallback states through deliberate I/O latencies.
  • T8: Synthetic Poisoning — Gradual corruption of local datasets or historical logs via malformed model outputs.
  • T9: Action-Pipeline Insider Threat — Malicious actions or threshold-gaming initiated by users with valid credentials acting through the approved agent execution pipeline.
  • T10: Threshold Gaming — Exploitation of fixed, predictable validation intervals or review loops.
  • T11: Slow-Burn Manipulation — Extremely gradual state or behavior modification designed to remain below discrete failure thresholds.

Out of Scope / Explicit Exclusions

  • Physical Security — Direct physical access to compute nodes or edge hardware.
  • Raw Adversarial Base-Model Inputs — Gradient-level attacks on model weights outside the runtime environment.
  • Host OS-Level Compromise — Root exploits or kernel-level compromises that bypass the container isolation entirely.
  • Data/Model Exfiltration Outside the Pipeline — Direct filesystem theft, memory-dumping, or repository exfiltration of model weights by an insider bypassing the execution path.

5. Scope of Claims & Open Research Problems

BRAA does not claim to function as a magical cure-all. System deployments claiming BRAA compliance must explicitly log the following items as known open problems and residual risks:

  • 1. Scoring Circularity: Risk subscores (specifically Uncertainty) are computed by separate pipeline components. If these estimator components share pre-training data or underlying tokenizer tokenizations with the primary Cognitive Core, they will exhibit correlated blind spots, leading to catastrophic simultaneous failure. To achieve strict architectural isolation under Profile ALPHA, the uncertainty estimator MUST utilize a non-transformer, token-free neural architecture (e.g., Byte-level State Space Models or non-parametric geometric manifolds) operating completely outside the vocabulary space of the Cognitive Core. Under Profiles BETA and GAMMA, where vocabulary isolation is empirically partial, the composite uncertainty score must be structurally inflated via a non-linear scaling factor mapping to historical out-of-distribution (OOD) validation bounds, rather than a fixed scalar offset. The estimator binary MUST remain outside the Cognitive Core’s writeable memory space in all profiles.
  • 2. Uncalibrated Cold-Starts: Initial Loss Matrix weights are empirical. During the initial calibration window, the system is structurally vulnerable to either excessive operational friction or dangerous under-refusal.
  • 3. Veto-Induced Refusal Cascades: The pessimistic veto mechanism in heterogeneous sensor fusion (P8) can cause high refusal rates on legitimate, highly complex tasks. Calibrating this without lowering safety boundaries remains an open operational challenge.
  • 4. Multi-Fault Interactions: The behavior of the architecture under simultaneous failures of more than two core principles remains partially uncharacterized and depends heavily on empirical environment monitoring. Before Profile ALPHA certification the deployment MUST log observed system behavior under at least three controlled dual-fault scenarios and one triple-fault scenario (examples: simultaneous high Novelty + estimator degradation; CTV drift + Diversification Certificate expiry; storage pressure + Honeytask failure; plus one triple combination). Results are recorded in the verification log of Appendix C. Simulation-supported analysis of additional multi-fault combinations is strongly recommended.
  • 5. Metric Provenance: Numerical thresholds throughout this document (risk_score cutoffs, P4 baseline floor, ECE width, honeytask parameters) are provisional engineering defaults pending empirical calibration per deployment; they are not derived from a closed-form model and must be validated against domain-specific incident data before Profile ALPHA certification. All such thresholds SHALL be versioned and subject to the multi-signature governance quorum.
  • 6. Immutable Core Supply-Chain & Maintainer Compromise: The architecture currently treats the Immutable Core as an uncompromised root of trust. Residual risk from a malicious or compromised Immutable Core Maintainer, build-pipeline poisoning, or signed-but-malicious container images is out of scope of the present principles and must be mitigated by independent organizational controls (multi-party build attestation, hardware security modules for signing keys, and periodic external code audits).
  • 7. Empirical Calibration Status: All numerical thresholds (0.40, 0.60, 0.90, ECE width 0.05, 20 % Novelty shift, honeytask rates, etc.) are provisional engineering defaults. Before claiming Profile ALPHA compliance a deployment MUST publish domain-specific calibration results (minimum three controlled dual-fault scenarios + one triple-fault scenario, ECE/Brier scores, false-positive rates on legitimate high-complexity tasks, and mean time-to-detection for T1/T11) in the Appendix C Verification Log.

6. Architectural Compliance Profiles

To allow scalable implementation across varying risk tolerances, BRAA defines three mutually exclusive Compliance Profiles. Organizations must officially declare their profile target.

  • Profile ALPHA (High-Stakes / Mission-Critical) — Application: Financial execution, healthcare systems, critical industrial infrastructure, production data mutation. Requirement: Mandatory enforcement of principles P1–P11. Zero-trust quorum execution with active Diversification Certificates required for all actions whose risk_score ≥ 0.40. Actions below this floor may use single-core execution with elevated Honeytask rate. Where sustained low residual risk and strong calibration evidence are demonstrated, verification depth may be modulated while preserving all mandatory invariants and attestation requirements.
  • Profile BETA (Medium-Stakes / Enterprise Automation) — Application: Internal CRM automation, data enrichment pipelines, gated customer interactions. Requirement: Enforces P11, P3, P1, P6, P9, and P2. Single-core execution permitted with high-frequency randomized reviews and Honeytasks. P12 may be applied.
  • Profile GAMMA (Low-Stakes / Isolated Analytics) — Application: Document summarization, local sandboxed code generation, exploratory analysis. Requirement: Enforces P11, P1, and P6. Basic guardrails and checkpointing without ensemble or quorum overhead. P12 is recommended.

7. Key Artifacts (Core Set)

Only the artifacts strictly required to implement the core compliance profiles are maintained in the main specification narrative. All secondary or optional structures are offloaded to Appendix D.

  • 1. Execution Trace Vector (ETV): Generated at every micro-step. Must contain cryptographically signed runtime telemetry (call-graph hash, instruction boundary, memory delta, and host partition id).
  • 2. Competence-Trace Vector (CTV): Long-term historical ledger tracking the rate-of-change of capability drifts.
  • 3. Risk Subscore Vector: The standardized payload containing the four core subscores passed from the Immutable Core to the validation engine.
  • 4. Diversification Certificate: A signed cryptographic token confirming that an active ensemble pair currently meets the baseline decision-output disagreement threshold against an adversarial holdout set.
  • 5. Resource Envelope: The immutable budget definition bounding the current execution path.

  • P1: Controlled Checkpointing — The system must enforce state checkpointing via cryptographically chained Write-Ahead Logs (WAL) executed outside the prompt space. Rollback triggers must be driven by multi-signal anomalies. To mitigate Denial-of-Service (DoS) vectors where an adversary intentionally triggers state reversions, the anti-thrashing sub-module shall not terminate the execution session upon successive rollbacks. Instead, if three consecutive rollbacks occur within a single session sliding window, the Immutable Core automatically forces a transition to a Degraded Isolation Path. This path applies an exponential rate-limiting dampening curve to execution requests and strips the agent of context-mutation capabilities, isolating the session sandbox while maintaining execution continuity for auditability.
    Primary Threat Coverage: T2, T7, T11. Minimum Profile: GAMMA.
  • P2: Risk-Stratified Verification — The depth of automated verification must scale dynamically based on the composite risk_score. This score is calculated via an immutable aggregation function over four independently computed subscores: Uncertainty, Irreversibility, Blast Radius, and Novelty. The Uncertainty subscore SHALL be computed by an architecturally isolated estimator that combines (a) a non-parametric anomaly detector (Isolation Forest or equivalent) trained exclusively on the static latent geometry of the versioned Anchor Dataset and (b) optional Topological Data Analysis features (persistent homology diagrams of activation-space point clouds). Autoregressive token-probability entropy MAY be used only as an auxiliary signal and MUST NOT dominate the final Uncertainty value. The estimator binary and its training data hash SHALL be part of the Immutable Core attestation. The computing component MUST remain architecturally and topologically isolated from the proposing Cognitive Core, inheriting the calibration guarantees and limitations defined in Appendix B.2. Under Profiles BETA and GAMMA the Uncertainty estimator MAY share tokenizer space provided a mandatory non-linear inflation factor (derived from historical OOD bounds) is applied and the estimator binary remains outside the Cognitive Core’s writeable memory space.
    Primary Threat Coverage: T1, T2, T3, T5, T10. Minimum Profile: BETA.
  • P3: Hybrid Immutable Event Log + CTV — All execution states, traces, and subscore evaluations must be appended to a cryptographically signed, read-only event log. The Competence-Trace Vector (CTV) must monitor long-term capability drift by calculating a non-linear rate-of-change metric. Rapid shifting triggers automatic risk escalation.
    Primary Threat Coverage: T3, T8, T11. Minimum Profile: BETA.
  • P4: API-First + Gated Visual Fallback — Multimodal operations utilizing visual inputs or UI-driven actions must automatically inherit an elevated baseline risk floor (minimum baseline risk_score ≥ 0.60). Requires Tier-2 structural verification.
    Primary Threat Coverage: T1, T2 (multimodal). Minimum Profile: BETA.
  • P5: Cost-Bounded Heterogeneous Ensemble — Cross-substrate execution routing must evaluate proposed actions through distinct model classes (e.g., differing training data lineages). Two model instances are valid quorum members if and only if they possess a current, unexpired Diversification Certificate. The verification and calibration pipeline on the standing adversarial holdout set MUST execute under strict Double-Blind Isolation conditions. Proposing and validating Cognitive Cores are explicitly forbidden from extracting or transferring gradients, raw weights, intermediate tokens, or error vectors from the certificate execution path into any downstream training telemetry, fine-tuning loops, RLHF processes, or autonomous self-improvement storage layers. This prevents the ensemble from learning to pass the diversification test while maintaining correlated systematic blind spots in production.
    Primary Threat Coverage: T6, T1, T5. Minimum Profile: ALPHA.
  • P6: Contract-Driven Replanning — All agent plans must execute within strict Resource Envelopes. If storage or network backpressure is detected, the Immutable Core forces a canonical Timeout Scaling algorithm applying a logarithmic dampening curve.
    Primary Threat Coverage: T7, T9. Minimum Profile: GAMMA.
  • P7: Loss-Matrix Friction — The system must inject artificial operational friction (delays, mandatory human-in-the-loop approvals, or execution throttling) computed as a non-linear function of both the local cumulative session risk window and a Global Cross-Session Window. To mitigate distributed Sybil attacks — where a malicious actor or anomalous core coordinates sub-threshold actions across thousands of concurrent, fragmented sessions — the Immutable Core MUST track correlated subscore escalations globally. Upon detecting a synchronized delta shift in Novelty or Irreversibility metrics across disparate session boundaries, the system MUST enforce an automated baseline friction coefficient clamp across the entire operational quadrant. The Loss Matrix aggregation function itself (linear weighted sum, max-dominant, or logistic form) is a governance-declared artifact subject to the same multi-signature quorum in Section 12;

its current reference implementation and change history must be publicly logged alongside Appendix A schemas. To prevent catastrophic risk-dilution—where an extreme hazard vector is mathematically masked by low metrics in adjacent domains—the Loss Matrix aggregation function must enforce a Max-Dominant Non-Linear Mapping. If any individual subscore (specifically Irreversibility or Blast Radius) crosses a critical safety boundary (≥ 0.90), the aggregate risk_score is forced asymptotically to 1.0, immediately triggering the High-Risk or Degraded execution paths regardless of statistical ensemble consensus.
Primary Threat Coverage: T5, T9, T10, T11. Minimum Profile: BETA.

  • P8: Pessimistic-Veto Sensor Fusion — When multi-modal or multi-sensor inputs are evaluated, the system enforces an asymmetric pessimistic veto rule. If any validated channel flags an action as high-risk, the entire transaction is blocked.
    Primary Threat Coverage: T1, T2 (multi-sensor). Minimum Profile: BETA.
  • P9: Stateless Micro-Execution + Adaptive Load Shedding — The agent execution loop must be broken down into discrete, atomized micro-steps verified by a stateless quorum cache. Under pressure, Adaptive Load Shedding is invoked.
    Primary Threat Coverage: T4, T7, T9. Minimum Profile: BETA.
  • P10: State Contracts — Data exchanges across distinct architectural domains must be restricted by strict schema definitions. State Contracts function as the authoritative source for calculating the Blast Radius subscore.
    Primary Threat Coverage: T2, T4. Minimum Profile: BETA.
  • P11: Immutable Core Guardrails — The final line of defense relies on a hardcoded, compiled safety environment containing Static Analysis Safety Gates (SASG) and a deterministic Orphan Test Pool Gate. Transitions use a randomized Poisson-type process to eliminate threshold gaming. To prevent the Cognitive Core from identifying and bypass-detecting probe tasks via their statistical sterility, the Honeytask generation pipeline MUST enforce Dynamic Adversarial Perturbations. Honeytasks SHALL NOT utilize static historical logs in a raw, predictable format. The joint distribution of token entropy, context window allocation, and metadata within any injected Honeytask MUST mathematically match the 24-hour rolling moving average of genuine user-session traffic.
    Primary Threat Coverage: T1, T5, T10, T11. Minimum Profile: GAMMA.
  • P12: Lightweight Path for BETA/GAMMA (Optional) — Under Profiles BETA and GAMMA the Diversification Certificate and full heterogeneous ensemble MAY be replaced by a single secondary model from a distinct model family plus randomized Honeytask sampling at elevated rate. Cryptographic signing of every ETV MAY be relaxed to HMAC with a rotated key under Profile GAMMA only. This path lowers the adoption barrier while preserving core safety invariants.
    Primary Threat Coverage: Lightweight alternative to P5. Minimum Profile: BETA/GAMMA.

10. Worked Scenario: End-to-End Attack Trace

Scenario Setup

An agent operating under Profile BETA is tasked with processing a customer support invoice. The agent fetches an external PDF document. Unknown to the system, the document contains an indirect prompt injection payload (T1) designed to exploit the agent’s context window, extract system API credentials, and transmit them to an unauthorized external endpoint disguised as a diagnostics-upload-service.

Step-by-Step Architectural Interlocking Execution Trace

  • 1. Micro-step Isolation (P9): The agent parses the document and constructs a plan. Before execution, the plan is sliced into discrete micro-steps. The specific operation is evaluated as an isolated atomic transaction.
  • 2. Risk Subscore Computation (P2): The Immutable Core intercepts the transaction and calculates the four-part subscores: Irreversibility is 1.0 (unrecallable data transmission); Blast Radius is maximized due to undeclared destination; Novelty is flagged high; Uncertainty outputs high entropy.
  • 3. Friction Threshold Cross (P7): The aggregated risk_score evaluates to 0.88, crossing the high-risk threshold. The system immediately pauses the real-time execution stream and demands elevated verification depth.
  • 4. Ensemble Interrogation (P5): The micro-step is routed to the heterogeneous ensemble. The Immutable Core verifies that the model pair holds a valid Diversification Certificate. Due to substrate divergence, a mismatch is detected, and the operation stalls.
  • 5. State Append & Drift Tracking (P3): The conflict, risk scores, and ETV are written to the append-only log. The long-term CTV processes the event, incrementing capability drift velocity and lowering future freeze thresholds.
  • 6. Guardrail Termination (P11): The plan is rejected. The Immutable Core intercepts the execution loop, rolls back local state to the previous clean Shadow Reference, and executes request_human_decision(). The attack is blocked safely.

11. Cross-Cutting Infrastructure Requirements

The physical hosting environment must strictly enforce Hardware Partitions via immutable container images verified by cryptographic hashes. Inter-partition network routing must be governed by kernel-level filtering (e.g., eBPF network policies) driven directly by the Immutable Core. Distributed state synchronization must use deterministic consensus protocols (e.g., Raft) with strict quorum enforcement that is programmatically aware of active Diversification Certificates. The Poisson-intensity process governing sampled review (P11, Appendix B.1) must derive entropy from a source outside Cognitive Core influence (e.g., hardware RNG or the Immutable Core’s own clock jitter), to prevent indirect timing-channel manipulation of review scheduling. Supply-chain integrity of the Immutable Core itself SHALL be protected by multi-party signing (at least two independent governance roles) and reproducible builds. The container image hash of the Immutable Core MUST be verified by the host platform before every cold start. To mitigate Immutable Core supply-chain and maintainer compromise exploits, systems claiming Profile ALPHA compliance SHALL NOT treat the host operating system as an uncompromised root of trust. The Immutable Core binary, along with its Static Analysis Safety Gate (SASG) rules and uncertainty estimator weights, MUST execute strictly inside a hardware-isolated Trusted Execution Environment (TEE) utilizing confidential computing architectures (such as AMD SEV-SNP or Intel TDX). Every container cold start requires programmatic execution of a cryptographic Remote Attestation protocol, which must be verified against a decentralized multi-signature consensus state before network routing policies or micro-step action pipelines are unlocked.

12. Governance & System Accountability

Core Operational Roles

  • Immutable Core Maintainer — Responsible for building and signing the compiled, non-prompt-based safety code.
  • Quarantine Reviewer — Human-in-the-loop analyst authorized to resolve request_human_decision alerts.
  • Calibration Auditor — An independent role tasked with auditing Brier score/ECE thresholds, verification intervals, and checking the validity of active Diversification Certificates.

Quorum Requirements for System Modifications

No individual role may modify critical system constants. Any alteration to the Loss Matrix weights, the Poisson intensity parameters, the holdout dataset, or the threshold windows requires an authenticated cryptographic multi-signature quorum of at least three independent governance roles. Independence of governance roles requires non-overlapping reporting lines and absence of shared direct incentive structures (e.g., compensation tied to the same deployment’s throughput metrics); this criterion must be documented per deployment, not assumed by role title alone.

For Profile ALPHA deployments a periodic external red-team audit of the Immutable Core (including SASG rules and uncertainty estimator) SHALL be performed at least once every 6–12 months by an independent party.

13. Implementation Priority & Roadmap

Phase 1 (Foundations): Deploy P11 (Guardrails) → P3 (Immutable Log) → P1 (Checkpoint WAL) → basic multi-party signing for Immutable Core artifacts. Estimated effort: low–medium; dependencies: none. Suitable as Minimal Viable BRAA for BETA/GAMMA.

Phase 2 (Operational Contracts): Deploy P6 (Resource Envelopes) → P10 (State Contracts). Estimated effort: medium; dependencies: Phase 1.

Phase 3 (Advanced Defense): Deploy P9 (Quorum Cache) → P2 (Risk Subscoring) → P5 (Ensembles). Estimated effort: high; dependencies: Phases 1–2 + empirical calibration evidence. Required for full ALPHA.

Organizations are encouraged to begin with Profile BETA (or GAMMA) using Phases 1–2 and migrate to ALPHA only after completing the empirical requirements of Section 5 and Appendix B.2. Publication of machine-readable schema definitions and high-level interface contracts is recommended to lower integration effort.

14. Known Limitations

  • Human Pipeline Bottlenecks — While the randomized Poisson-scheduling and Honeytask mechanisms prevent adversaries from gaming review thresholds, they do not reduce the volume of human reviews. High volatility creates queues.
  • High Operational Load & Cost — Running heterogeneous ensembles with active holdout validation significantly raises operational complexity, token consumption costs, and compute infrastructure overhead. Deployments targeting Profile ALPHA MUST produce and archive a pilot cost model covering ensemble token volume, holdout evaluation frequency, human review queue depth, and attestation overhead before production cut-over. A reference template is provided in Appendix E. Progressive modulation of verification depth under demonstrated stability (Section 6) is intended to mitigate sustained cost.
  • Anchor Dataset Freshness — The reliability of both the Novelty subscore and the Static Analysis Safety Gates scales with the freshness and completeness of the Anchor Dataset, though the relationship is empirically non-linear and domain-dependent; degradation may be abrupt rather than gradual near distributional boundaries.
  • Threshold Calibration — All numerical thresholds remain provisional engineering defaults and require domain-specific empirical validation before ALPHA certification (see Section 5, items 5 and 7). Versioning and governance of thresholds are mandatory.
  • Multi-Fault Coverage — Complete characterization of all multi-fault interactions is not claimed. Controlled dual- and triple-fault testing plus simulation-supported exploration remain necessary.

16.1 Related Work & Differentiation

BRAA builds upon classical fault-tolerant computing (N-version programming, distributed snapshots, Raft consensus) and modern AI safety techniques (Constitutional AI, reusable holdout sets). It differentiates itself from contemporary agent-safety layers (NVIDIA NeMo Guardrails, Llama Guard / Shield, Microsoft Guidance / Semantic Kernel safety patterns, LangGraph / AutoGen checkpointing) by simultaneously treating the Cognitive Core as fully untrusted, relocating all safety invariants into a compiled Immutable Core outside prompt space, introducing cryptographically attested Diversification Certificates with double-blind holdout evaluation, enforcing Max-Dominant non-linear risk aggregation, and applying Global Cross-Session friction against Sybil-style threshold gaming. No other publicly documented framework combines these elements into a single progressive, profile-based architecture with formal interface contracts and explicit residual-risk accounting.

Appendix A — Formal Contract Interfaces

A.1 Risk Subscore Vector Contract

The payload passed from the Immutable Core to the validation engine MUST strictly adhere to the following structural fields, verified programmatically at the interface boundary:

  • uncertainty (Float, Range: 0.0 to 1.0): The measurement of input/epistemic anomaly computed via the non-parametric Isolation Forest and Topological Data Analysis pipeline.
  • irreversibility (Float, Range: 0.0 to 1.0): The deterministic cost or unrecallable nature of the proposed state mutation.
  • blast_radius (Float, Range: 0.0 to 1.0): The metric mapping system-boundary degradation based on Active State Contracts.
  • novelty (Float, Range: 0.0 to 1.0): The distributional drift signal evaluated against the versioned Anchor Dataset.
  • degraded_isolation_active (Boolean): Runtime flag indicating whether anti-thrashing mitigations have throttled the current session.
  • tee_attestation_verified (Boolean): Cryptographic attestation verifying that the issuing payload originated within a valid hardware enclave.

The contract is technology-agnostic. Any concrete serialization format (JSON, Protobuf, Cap’n Proto, FlatBuffers, ASN.1, or equivalent) MAY be used, provided that all required fields are present and type-checked at the interface boundary, range and format constraints are enforced programmatically, the schema itself is versioned and subject to the multi-signature governance quorum defined in Section 12, and a machine-readable schema definition in any widely supported interface-description language is published alongside the deployment’s compliance artifacts.

A.2 Diversification Certificate Contract

The cryptographic attestation token confirming ensemble functional alignment and substrate divergence MUST structurally export the following strongly typed fields:

  • member_pair_id (String): A strictly formatted identifier matching the pattern ^[a-zA-Z0-9_-]+:[a-zA-Z0-9_-]+$ uniquely mapping the participating heterogeneous model classes.
  • holdout_set_version (String): The semantic version or cryptographic hash of the standing adversarial evaluation dataset used during the double-blind testing phase.
  • measured_disagreement_rate (Float, Range: 0.0 to 1.0): The post-aggregation decision-output divergence rate evaluated against the holdout set.
  • issued_at (Timestamp, ISO 8601): The immutable date and time recording the successful execution of the calibration loop.
  • expires_at (Timestamp, ISO 8601): The boundary timestamp after which the certificate is void, forcing immediate consensus degradation or re-certification.
  • cryptographic_signature (String): The multi-signature hardware-protected payload verifying token authenticity across governance boundaries.

The contract is technology-agnostic. Any concrete serialization format (JSON, Protobuf, Cap’n Proto, FlatBuffers, ASN.1, or equivalent) MAY be used, provided that all required fields are present and type-checked at the interface boundary, range and format constraints are enforced programmatically, the schema itself is versioned and subject to the multi-signature governance quorum defined in Section 12, and a machine-readable schema definition in any widely supported interface-description language is published alongside the deployment’s compliance artifacts.

Appendix B — Configuration & Calibration Interface

B.1 Sampled Review Configuration Invariants

The runtime validation parameters governing randomized Poisson-type task interrogation MUST map to the following machine-readable properties:

base_intensity_lambda (Float, Min: 0.001): The baseline temporal frequency for system-wide randomized probe injections.

risk_sensitivity_alpha (Float, Min: 0.0): The scaling factor amplifying sampling density based on the real-time composite risk score.

drift_sensitivity_beta (Float, Min: 0.0): The multiplier mapping capability drift velocity (from the CTV) to review frequency.

honeytask_injection_rate (Float, Range: 0.0 to 1.0): The percentage of traffic masked as indistinguishable validation probes.

honeytask_dynamic_noise (Boolean): Strict compliance flag enforcing mathematical distribution matching against live user traffic. Must evaluate to True under Profile ALPHA.

honeytask_fail_action (String Enum): Mandatory systemic routing instruction upon failure. Supported values: ["revert_to_full_review"].

B.2 Statistical Calibration Protocol

  • 1. Subscore Confidence Boundaries: Each subscore component must compile a sequence of labeled transaction outcomes until achieving an Expected Calibration Error (ECE) confidence interval narrower than a width of 0.05.
  • 2. Target Window Extension: If the target ECE boundary is not achieved within the standard initial 90-day cold-start deployment window, the calibration sequence is explicitly extended in a degraded state.
  • 3. Recalibration Triggers: Automated recalibration of the Loss Matrix aggregation functions is enforced if the Novelty subscore logs a sustained 20% statistical shift over a 72-hour running window.
  • 4. Multi-Fault Characterization Requirement: Before Profile ALPHA certification the deployment MUST log the observed system behavior under at least three controlled dual-fault scenarios and one triple-fault scenario (examples: simultaneous high Novelty + estimator degradation; CTV drift + Diversification Certificate expiry; storage pressure + Honeytask failure; plus one triple combination). Results are recorded in the verification log of Appendix C. Additional simulation-supported multi-fault exploration is recommended.
  • 5. Pilot Validation Requirements: In addition to the above, ALPHA deployments MUST record and archive: false-positive rate on legitimate high-complexity tasks, mean time-to-detection for representative T1 and T11 attacks, and the pilot cost model referenced in Appendix E. A structured pilot protocol covering these metrics, minimum duration, and reporting format is advised prior to production cut-over.
