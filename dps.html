Deterministic Predictive State (DPS) Architecture for High-Latency Interplanetary Command and Control

1. Abstract

Round-trip light-time delays between Earth and Mars routinely reach 20–40 minutes. Under these conditions conventional transactional databases and consensus protocols either lock up or time out.

This paper describes a practical architecture that avoids the problem by running identical, bit-for-bit deterministic simulators on the ground and on the spacecraft. All calculations use software fixed-point arithmetic. Both sides share the same atomic-clock timeline (corrected for relativity) and the same sequence of pseudorandom seeds. When delayed telemetry arrives via DTN, the ground side rewinds its state to the timestamp of the data, merges the real measurements with CRDTs, and fast-forwards the simulation back to the present. Operators therefore work with a continuously updated predictive view that converges to the true spacecraft state once the data catch up.

The method is restricted to fully deterministic workloads: trajectory propagation, attitude dynamics, power and thermal modelling, and resource scheduling.

2. Background

Deep-space links are limited by the speed of light. A command sent to Mars takes several to more than twenty minutes to arrive; the reply takes the same time to return. Ground teams need an accurate picture of the vehicle before they uplink the next set of commands. Lock-based or consensus databases cannot operate under these delays. Purely asynchronous approaches leave operators looking at stale data and risk divergence between the ground model and the actual vehicle.

What is required is a live predictive model that remains consistent with reality once the delayed telemetry arrives.

3. Related Work

Existing solutions fall into a few categories:

Delay/Disruption Tolerant Networking (DTN Bundle Protocol, LTP) solves reliable transport but does not address state consistency.

JPL’s Mission Data System and similar state-based architectures emphasise explicit state variables and models, yet still assume relatively short communication delays.

Model-predictive control is widely used for trajectory and attitude, but the prediction usually runs on one side only.

Deterministic lockstep simulation is common in multiplayer games and some multi-agent systems; shared PRNG seeds are a standard technique there.

Conflict-free replicated data types (CRDTs) provide eventual consistency in terrestrial distributed systems.

The combination described here—bit-identical fixed-point simulators on both ends of a high-latency link, timeline-indexed shared seeds for environmental noise, and a CRDT-based rewind-merge-fast-forward correction—does not appear in the literature the author has examined.

4. Architecture

The system runs the same simulation code on the ground servers and on the flight computer.

Fixed-point arithmetic

Floating-point arithmetic is avoided. All calculations (orbital mechanics, attitude dynamics, power, thermal) use software fixed-point formats such as Q32.32 or Q64.64. Rounding mode, memory layout and overflow behaviour are defined identically on both platforms. This guarantees that the two simulators produce exactly the same bit patterns even when one side runs on x86 servers and the other on a radiation-hardened processor.

Shared timeline and random seeds

Both sides maintain a common time base derived from atomic clocks and corrected for relativistic effects (post-Newtonian terms or equivalent ephemeris data). A pre-agreed sequence of pseudorandom seeds is indexed by this timeline. When the simulation needs to model a semi-random physical effect (solar radiation pressure variations, thruster performance scatter, residual drag, etc.), both sides draw the same seed for that time step. No noise samples travel over the link.

A practical indexing scheme is:

seed(t) = hash(base_seed, floor(t / Δt))

or a simple sequential table loaded before launch.

Predictive horizon on the ground

The ground simulator runs continuously in real time. Controllers see and interact with a live predicted state. Commands can be tested against this prediction before uplink.

Telemetry transport

Sensor data and event logs travel via the DTN Bundle Protocol (or any equivalent delay-tolerant protocol). Each bundle carries a high-resolution timestamp of the moment the event occurred on the spacecraft.

Correction process

When a delayed bundle arrives the ground system performs the following steps:

Rewind the internal state to the exact timestamp of the bundle (or to the nearest earlier checkpoint if continuous state history is not kept).

Compute the difference between the earlier prediction and the actual measurements.

Merge the difference using commutative CRDT operations (G-Counters for cumulative quantities, OR-Sets for sets of events, LWW-registers for last-writer-wins values, etc.).

Fast-forward the simulation from the corrected point to the current wall-clock time, applying the same deterministic dynamics and the same seed sequence.

Update the operator displays with the corrected predictive state.

Because the underlying simulation is deterministic and the CRDT merges are commutative and associative, the final state remains consistent regardless of the order in which bundles arrive.

Out-of-order or missing bundles are handled naturally: a later bundle simply triggers another rewind-merge-fast-forward cycle. Partial data are merged as far as they go; the missing portions continue to be predicted until they arrive.

5. Scope and Limitations

The architecture is deliberately limited to algorithmic, predictable subsystems:

n-body trajectory propagation and manoeuvre modelling

attitude determination and control

power system state-of-charge and load scheduling

thermal prediction of critical components

closed-loop environmental control

resource and memory scheduling

Non-deterministic or human-in-the-loop inputs (operator commands, unmodelled hardware failures, crew actions) enter the system through explicit injection points outside the core deterministic loop. Once injected, they become part of the shared history and are replayed identically on both sides.

The approach degrades gracefully when the physical model diverges too far from reality; the CRDT merge simply applies larger corrections. Extremely large state vectors may make frequent full rewinds expensive; in that case periodic checkpoints and incremental state deltas are used.

6. Implementation Notes

The fast-forward step must run substantially faster than real time so that the predictive display remains responsive.

Checkpoint frequency is a trade-off between memory and rewind cost; typical values are every few seconds to every minute depending on state size.

Both sides must agree on the exact fixed-point library, hash function for seeds, and CRDT implementations before flight.
