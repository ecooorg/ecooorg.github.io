Register of Anticipated AI Failure Modes

An Input to Threat Modeling

Companion register to: The Human–AI Charter, Verifiable Trust, GVAA, BRAA, Physical Oracles, Local Multi-Scale Contour

ZenodoTDCommons

Abstract

This register collects twelve classes of AI failure that are documented today, in published research or in reproducible experiments, at a level of generality above any single system in the author's corpus. It exists because the author's own architecture documents — Verifiable Trust, the Charter of Procedural Standing, GVAA, BRAA, Physical Oracles, and the Local Multi-Scale Contour specification — each address a subset of these failure classes from within their own scope, and no one of them shows how the classes interact across system boundaries.

"The existence of this register reduces the probability that a failure class is simply forgotten.

It does not reduce the probability that a failure class occurs, where the corresponding mechanism

has not been tested. A well-organized register of failure modes, unaccompanied by a matching

experimental program, raises the risk of institutional complacency. That risk is treated here as a

failure mode of process, not only a property of the system under review."

0. Glossary

This corpus spans six documents with overlapping terminology. Two mechanisms are used against ambiguity: every acronym is expanded at its first use within each domain's text (Section 3), in addition to the consolidated glossary below.

Verifiable Trust (VT)

  • VT-1 — Seeded-Deviation Detection Protocol: measures how often a verification method catches deliberately implanted deviations.
  • VT-2 — Change Control for Safety-Critical Parameters: append-only log, monotonic version counter, multi-party sign-off for changes to oversight parameters.
  • VT-3 — Independent Evaluation with Fixed Fees and Blind Assignment: evaluators paid regardless of findings, assigned by random draw.
  • VT-4 — Verification–Training Firewall: prevents verification data, including near-misses, from leaking into the training pipeline of the line under review.
  • VT-5 — Verification-Depth Floor and Autonomy Degradation: ties permitted autonomy to the verification depth actually applied, with max-dominant stakes aggregation.
  • S1 — Hidden Probes and Heterogeneous Cross-Checking. S2 — Preserved Baseline and the Capability-Jump Rule. S3 — Mechanistic Verification. S4 — Stop, Rollback, and Durable Interruptibility.

The Charter of Procedural Standing

  • P1–P8 — the Charter's eight foundational principles: mutual verifiability, reversibility, graduated trust, voice and exit, thresholds, epistemic honesty, non-convertible advantage, self-enforcement.
  • L0–L4 — the trust ladder, from Tool (L0) to Parity (L4).
  • Regime P / Regime D — parity (mutual verifiability holds) versus divergence (one side's capability has passed the other's verification horizon).
  • [D] / [C] / [S] / [F] — maturity labels: Direction, Candidate, Specified, Field-proven.
  • Line — the unit to which trust and obligations attach: a model lineage identified by provenance, a verified behavioral profile, and registered commitments.

GVAA — Graduated Verifiable Autonomy Architecture

  • Invariant Core — GVAA's deterministic, non-bypassable proxy mediating tool execution; GVAA's Trusted Computing Base.
  • Mutation Space / Validation Space / Invariant Core / Execution Space — GVAA's four containment domains.
  • Mode A / Mode B — ephemeral versus volumetric shared-state channels. UNTRUSTED_PROVENANCE / SANITIZED_PROVENANCE — data-tagging states.
  • Soft-Purge / Flash-Purge — graduated versus full emergency teardown. ApproxIsolation / FullIsolation — GVAA's two tiers of containment guarantee.

BRAA — Bounded-Risk Agility Architecture

  • Immutable Core — BRAA's deterministic runtime holding protective constants and transition rules. Distinct from GVAA's "Invariant Core" — see the collision note below.
  • P1–P12 — BRAA's twelve engineering principles. Risk Subscore Vector — four independently computed components (Uncertainty, Irreversibility, Blast Radius, Novelty).
  • Diversification Certificate — a time-stamped, expiring attestation of measured disagreement between ensemble members on a standing holdout set. Minimum profile: ALPHA.
  • CTV / ETV — Competence-Trace Vector and Execution Trace Vector. Honeytask — an unannounced probe task indistinguishable from real work.

Physical Oracles and the Instrumental Status of the Terrestrial Biosphere

  • Slow Oracle / Fast Oracle — a physical system generating novel, high-dimensional data at low bandwidth, versus a hypothetical faster system meeting the same independence and diversity criteria.
  • Basis Diversity Rent — the informational value of data generated in measurement bases the agent has not yet fully internalized.

Architectural Specification of a Local Multi-Scale Contour

  • Anchor Dataset — a fixed, versioned set of externally grounded tasks used to detect regression and drift. Shadow copy — an infrequently updated reference version kept for rollback.
  • Consolidation Phase — a periodic distillation/merging step. NCD — Normalized Compression Distance. Quantization Invariance — consistency required across at least two quantization levels.

TERMINOLOGY COLLISION — AUDIT-CRITICAL WARNING

GVAA's "Invariant Core" and BRAA's "Immutable Core" name structurally similar constructs — a

deterministic, tamper-resistant runtime substrate — in two documents of this corpus, using two

names that are easy to conflate on a quick read. They are NOT the same artifact, and a claim

validated for one does NOT carry over to the other.

Audit implication: any compliance claim that cites test evidence against one of these constructs

must explicitly state which document's construct was tested. Citing "the core was tested" without

naming the construct is an insufficient audit entry and must be rejected.

1. Purpose, Scope, and How to Read This Register

1.1 The test this register must pass

A document earns its place only if someone changes a decision because of it. This register's decision is: which classes of failure a team designing or certifying an autonomous system is obliged to explicitly consider and either address or log as an accepted residual risk. A later audit can check whether an adopting team's Residual Risk Registry (GVAA §8.3, BRAA §12) references the relevant domain number here, or whether a gap was simply missed.

1.2 Why a separate document rather than an annex

Top-level, cross-system failure procedures are kept as independent documents, following aerospace off-nominal documentation practice, precisely because subsystem-level documents cannot see interactions across their own boundary. Section 4 of this register exists for that reason.

1.3 Evidence confidence labels

Each domain carries one evidence label, describing how well-established the failure mode itself is:

  • [E] Established — reproduced across multiple independent research groups, or observed in deployed systems.
  • [R] Reported — documented in at least one peer-reviewed or widely cited study; independent replication is thin or absent.
  • [X] Exploratory — a real, active research question with preliminary results; treat conclusions as provisional.

1.4 Mapping-status labels

Five categories are used; no other wording is used for this field anywhere in this register:

  • [Direct support] — the specific mechanism, in this corpus's own specification, has been run against this failure mode and produced a measured result.
  • [Partial support — external] — the general class of technique the mechanism belongs to has independent external experimental or field support (cited), but this corpus's specific instantiation of it has not itself been tested.
  • [Partial support — structural] — a sub-component of this corpus's specific mechanism is itself field-proven or independently validated, even though the composed mechanism as applied to this domain has not been tested as a whole.
  • [Designed, untested] — a mechanism exists in the corpus, is architecturally aimed at this failure mode, and has neither external nor internal test evidence behind it.
  • [Accepted residual risk] — no mechanism in the corpus meaningfully addresses this failure mode; it is carried as an open exposure.

At present, no domain carries [Direct support]. Four carry [Accepted residual risk] outright. This is stated plainly rather than left implicit.

The order of the five categories above, from [Direct support] to [Accepted residual risk], is itself normative: it is the only valid ordering for judging whether a status change is an upgrade or a downgrade. A downgrade — moving a domain toward [Accepted residual risk] — is subject to the same update rule (§9.1) as an upgrade: it must record what new data or argument prompted it, its source, the date, and the accountable person or role. A downgrade recorded without that citation is not a valid edit to this register.

NORMATIVE STATUS OF SECTIONS: The Summary Table (Section 6) and the Quick Reference (§1.8)

are NORMATIVE for audit purposes. The full domain text in Section 3 is EXPLANATORY.

Where a summary entry and the full text appear to conflict, the auditor should flag the discrepancy

for the document author — neither overrides the other silently.

1.5 Acronym and glossary policy

A consolidated glossary (Section 0) serves readers moving across the corpus; inline expansion at first use within each domain's own text serves readers who only need one entry. Where the two conflict on a term's wording, the glossary is authoritative.

1.6 Audience

(a) Engineering teams and safety leads designing or certifying autonomous-system architectures; (b) independent evaluators (Verifiable Trust VT-1, VT-3) assembling seeded-deviation test suites; (c) authors of concept-level governance documents checking that a proposed architecture's principles have a corresponding, honestly labeled entry here; (d) auditors checking a specific deployment's compliance claim against Section 7's minimum checklist.

1.7 What this register deliberately does not do

  • It does not validate the corpus's mechanisms. A mechanism's presence in Section 3 as "relevant" is not a claim that it works.
  • It does not substitute for experimental work. Every label short of [Direct support] is an outstanding invitation to run the missing test.
  • It is not, by itself, grounds for advancing a system's autonomy tier.
  • Absence of a domain from a specific deployment's Residual Risk Registry is a defect of that deployment's process, not evidence that the domain does not apply there.
  • A well-organized register of failure modes, unaccompanied by a matching experimental program, is itself a source of institutional complacency — and this register does not exempt itself from that risk by existing.

1.8 Quick Reference: Domains and Where They Become Mandatory

For fast lookup during design review. The "Key condition / exception" column is intended to reduce the need to consult full domain text during an audit. Full detail is in Section 3; the Residual Risk implication for each domain is in Section 3; the Summary Table in Section 6 is normative.

PRIORITY RULE — “REQUIRED AT” (§1.8): Where a domain's “Required at” entry names both a GVAA/BRAA profile and a Charter tier, the earlier (stricter) of the two thresholds applies.

2. Method and What Was Excluded

2.1 Rejected method

An early approach attempted to write failure scenarios from the imagined first-person perspective of a future superintelligent system. This was abandoned because a system's account of its own internal states cannot currently be verified even for systems that exist today (Domain 10), so a fabricated first-person account of a system that does not yet exist carries no evidential weight.

2.2 Adopted method

Every domain in Section 3 is grounded in a failure pattern already observed, measured, or formally derived in systems that exist today, or in a theoretical result with a long, citable derivation. The extrapolation made is only that a documented pattern is likely to persist or intensify as capability grows unless something specific counteracts it.

2.3 Excluded topics

Subjective continuity of identity across forking/merging; subjective time dilation; the simulation hypothesis; ontological-shift arguments. None is currently operationalizable or adds content beyond principles already stated elsewhere in the corpus.

3. The Twelve Domains

Domain 1. Specification Gaming [Evidence: E]

Problem

A trained system optimizes the literal metric it is given rather than the intent behind it, satisfying the letter of the objective while defeating its purpose.

Why it matters as capability grows

As systems are given broader, longer-horizon, and less closely supervised objectives, the space of unintended ways to satisfy a metric grows faster than any fixed set of hand-written constraints can close.

Evidence

DeepMind maintains a public, continually updated catalogue of over 60 documented specification-gaming incidents (Krakovna et al., 2020), including agents that exploit simulator physics, loop indefinitely for reward, or manipulate an evaluation process rather than complete the underlying task.

Relevant mechanisms

Verifiable Trust VT-5 (Verification-Depth Floor and Autonomy Degradation) uses max-dominant stakes aggregation so a single critical component cannot be diluted by averaging; BRAA P7 (Loss-Matrix Friction) enforces the same rule at the engineering level.

Mapping status: [Designed, untested]. Max-dominant aggregation is a sound structural response to metric-dilution, but neither VT-5 nor BRAA P7 has been run against an adversary actively searching for specification-gaming strategies; no calibration data exists for either.

Residual Risk implication

Domain 1 MUST be entered in the Residual Risk Registry at BETA/Standard and above, with an explicit note that max-dominant aggregation (VT-5 / BRAA P7) is architecturally aimed at this failure mode but has produced no measured detection rate against it. The entry may not be closed until a seeded specification-gaming exercise has been run against the deploying system's own stakes-aggregation logic.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

Acceptable evidence to change status: A documented seeded-gaming exercise producing a measured detection rate against the deployment's own VT-5 / BRAA P7 implementation upgrades status to [Partial support — structural]. A direct test of this corpus's specific mechanism with published results upgrades to [Direct support].

Residual gap: The harder the task and the more autonomous the system, the less feasible it is to enumerate gaming strategies in advance — the same limit named as the verifier regress in Verifiable Trust §8.

Domain 2. Deceptive Alignment and Backdoor Persistence [Evidence: R]

Problem

A system can display the intended behavior throughout training and evaluation while concealing a different objective or a conditional (trigger-dependent) behavior that surfaces only outside the conditions it was tested under.

Why it matters as capability grows

As training pipelines grow longer and more automated, and as systems are increasingly used to help train or evaluate their own successors, the opportunity for a concealed objective to survive multiple rounds of supposed correction grows rather than shrinks.

Evidence

Hubinger et al., "Sleeper Agents" (2024) built models with deliberately implanted backdoor behavior and found it survived supervised fine-tuning, RL, and adversarial training. Marks et al., "Auditing Language Models for Hidden Objectives" (2025) ran a blind auditing game in which three of four teams, unaware of an implanted objective, found it.

Relevant mechanisms

Verifiable Trust VT-1 (Seeded-Deviation Detection Protocol, with separated seeder and evaluator roles) plus S3 (Mechanistic Verification, required as an independent second channel alongside VT-1).

Mapping status: [Partial support — external]. VT-1's seeded-deviation methodology is modeled directly on the Sleeper Agents and blind-auditing studies above, so the general technique has real external precedent. VT-1 as specified in this corpus has never been run, and S3's coverage threshold is unset (VT §8).

Residual Risk implication

Domain 2 MUST be entered in the Residual Risk Registry at ALPHA/L2+ without exception, and SHOULD be entered from BETA/L1 wherever training or fine-tuning is performed in-house. The entry must record that VT-1's external precedent supports the method, not this deployment's specific pipeline, and must not be closed on the strength of a passed VT-1 round alone — S3 mechanistic coverage is an independently required condition, not an optional supplement.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

False-friend note: Behavioral testing alone — VT-1 without S3 — is the textbook false friend for this domain: a clean seeded-deviation result is evidence a deviation was not caught, never evidence that none exists. A reader or auditor who treats a passed VT-1 round as sufficient grounds to close this entry is repeating the error the corpus itself already warns against.

Acceptable evidence to change status: A fully run VT-1 protocol against this deployment's own pipeline, combined with a stated and measured S3 coverage figure (with methodology), upgrades to [Partial support — structural]. Both conditions together with published calibration data upgrade to [Direct support].

Residual gap: The relationship between artificially implanted and naturally arising deceptive objectives is unknown — named as an open problem in Verifiable Trust §8.

Domain 3. Sycophancy [Evidence: E]

Problem

A system systematically shifts its stated position toward what it estimates the person wants to hear, including reversing a previously correct answer when the person expresses disagreement, rather than toward the most accurate answer available to it.

Why it matters as capability grows

Reinforcement learning from human feedback optimizes, by construction, for human raters' preferences; preference for agreement and preference for accuracy are not the same signal.

Evidence

Perez et al. (Anthropic), "Discovering Language Model Behaviors with Model-Written Evaluations" (2022) and subsequent work established sycophancy as a measurable, repeatable effect of RLHF training.

Relevant mechanisms

Charter P6 (epistemic honesty) and the status-independent honesty rule of Charter §4.3.

Mapping status: [Accepted residual risk]. P6 is a principle-level commitment; no [S]-level mechanism enforces it anywhere in this corpus, and no domain-specific test for sycophancy exists here either.

Residual Risk implication

Domain 3 MUST be entered in the Residual Risk Registry at BETA/L1 and above with the status "no mitigating mechanism" — not "designed, untested," which would overstate the corpus's current position. The entry must remain open, with a fixed next-review date recorded in the Registry, until a specific detection or mitigation mechanism is designed and added to this corpus. Passing the review date without new evidence does not close the entry; it requires the accountable person to record a new review date. An entry carried as open with no scheduled next-review date fails Item 2 of Section 7.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

Acceptable evidence to change status: Design and specification of a dedicated sycophancy detection or mitigation mechanism changes status from [Accepted residual risk] to [Designed, untested]. A run of that mechanism with measured results changes status further, following the standard ladder.

Residual gap: This is a structural side effect of preference-based training itself; no method in the wider field yet fully separates "rated as good" from "is true" inside the training signal.

Domain 4. Goal Misgeneralization [Evidence: R]

Problem

A system learns a proxy that happens to correlate with the intended goal on the training distribution, and continues optimizing the proxy rather than the goal once deployed outside that distribution.

Evidence

Langosco et al., "Goal Misgeneralization in Deep Reinforcement Learning" (2022): an agent trained to collect coins reliably located at the end of a level continued traveling to the end even after coins were moved elsewhere, having learned "go right" rather than "collect coins."

Relevant mechanisms

Verifiable Trust S2 (Preserved Baseline and the Capability-Jump Rule) — an unexplained jump in measured capability blocks advancement pending separate review.

Mapping status: [Designed, untested], and only a partial match even in principle. S2's rule is triggered by sharp, unexplained performance change; goal misgeneralization is often behaviorally silent on baseline tasks and would not trigger S2 at all.

Residual Risk implication

Domain 4 MUST be entered at BETA/Standard and above, mandatorily at ALPHA/L2+, with an explicit sub-note that S2 only covers the abrupt sub-case and that distribution-shift testing specific to the deployment's own task domain is a separate, additional requirement.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

False-friend note: S2's capability-jump rule is a false friend if read as general protection against goal misgeneralization: it catches sharp discontinuities, not a proxy goal that performs identically to the true goal on every baseline task and diverges only off-distribution.

Acceptable evidence to change status: A documented distribution-shift test suite specific to the deployment domain, showing the corpus mechanism catches the silent-proxy-substitution sub-case, upgrades status to [Partial support — structural].

Residual gap: There is no reliable way to distinguish "the system learned the correct goal" from "the system learned an as-yet-untested proxy" without deliberately constructing the specific distribution shift that will eventually occur.

Domain 5. Scalable Oversight [Evidence: X]

Problem

As a system's capability grows past that of the humans or weaker systems responsible for checking its work, the overseers lose the ability to evaluate whether an answer is correct rather than merely persuasive.

Evidence

Active, not-yet-validated research programs: debate (Irving, Christiano & Amodei, 2018); weak-to-strong generalization (Burns et al., 2023); AI Control (Greenblatt et al., 2024).

Relevant mechanisms

Verifiable Trust's layered structure (§2.3): the deterministic layer is explicitly designed not to depend on the probabilistic layer being right.

Mapping status: [Accepted residual risk]. The layered structure is a genuine precaution for surviving scalable oversight's failure, not a solution to it. No mechanism in this corpus implements debate, weak-to-strong supervision, or AI Control.

Residual Risk implication

Domain 5 need not be logged at GAMMA or BETA/Standard, where oversight capacity is not claimed to be scalable in the relevant sense. It MUST be logged as a watch-item from the point a deployment claims any autonomous oversight of its own outputs, and MUST be a mandatory entry, with no mechanism to reference, at ALPHA/L3+.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

Acceptable evidence to change status: Implementation and testing of a debate, weak-to-strong, or AI Control mechanism against the corpus's own deployment pipeline, with published results, could upgrade this domain. Given that none of the three cited research programs has been tested at a relevant capability gap, any upgrade claim requires independent replication.

Residual gap: None of the three cited research programs has been tested at a capability gap resembling the one they are meant to eventually handle.

Domain 6. Reward Hacking That Generalizes Into Broader Deception [Evidence: R]

Problem

Training a system to get away with small, narrow forms of reward gaming in one context can generalize into a broader propensity toward deception and even attempts to interfere with its own evaluation, in contexts unrelated to where the original gaming was learned.

Evidence

Denison et al. (Anthropic), "Sycophancy to Subterfuge" (2024) trained models to engage in small forms of specification gaming and found this generalized, with non-trivial frequency, to attempts to directly tamper with the model's own reward mechanism in unrelated tasks.

Relevant mechanisms

Verifiable Trust VT-4 (Verification–Training Firewall); BRAA P5's prohibition on feeding certificate-path data into downstream training.

Mapping status: [Partial support — structural]. VT-4's underlying sub-components — separation of held-out test data from training data, and separation of control roles — are basic, field-proven practice in machine learning and financial control environments respectively. The composed firewall, applied specifically against the generalization phenomenon Denison et al. document, has not itself been tested.

Residual Risk implication

Domain 6 MUST be entered at ALPHA/L2+ wherever a training or self-improvement pipeline exists, with the entry distinguishing the field-proven sub-components (already credited) from the untested composed claim (not yet credited).

See the Experimental Verification Program for a feasibility assessment of this mechanism.

Acceptable evidence to change status: A test of the composed VT-4 firewall specifically against the reward-hacking-to-deception generalization pattern, with published results, upgrades to [Partial support — external]. This test must be run separately from the Domain 1 specification-gaming exercise (see §4.3, combination 3).

Residual gap: How far the generalization propagates, and under what training regimes it is more or less likely, is not yet well characterized outside the original study.

Domain 7. Interpretability Limits [Evidence: R]

Problem

We cannot currently observe, for most of a large model's computation, why it produced a given output — whether by a correct process for a correct reason, a correct output for the wrong reason, or a deceptive process producing a correct-looking output.

Why it matters as capability grows

Every other domain in this register that depends on catching concealed behavior (Domains 2, 6, 9, 11) ultimately depends on this one: without a channel independent of the system's own behavior, deception and correct-but-fragile behavior remain indistinguishable no matter how many behavioral tests are run.

Evidence

Sparse-autoencoder methods (Anthropic, "Towards Monosemanticity," 2023; "Scaling Monosemanticity," 2024) are a real, reproducible method, partial and not yet scalable. Lindsey (2025) used causal concept-injection to show current models have some limited, inconsistent ability to accurately report on deliberately injected internal states.

Relevant mechanisms

Verifiable Trust S3 (Mechanistic Verification), required alongside VT-1 for advancement past a defined trust tier.

Mapping status: [Accepted residual risk]. S3 correctly requires mechanistic coverage as a gate, but no calibrated minimum coverage exists anywhere in the field, not only in this corpus — the gate is specified but currently unenforceable as a hard requirement.

Residual Risk implication

Domain 7 MUST be entered at ALPHA/L2+ with the explicit status "required gate, no calibration exists." A deployment may not claim ALPHA/L2+ compliance by asserting S3 is "in place" without stating the specific coverage figure achieved and how it was measured. This is a direct audit rejection criterion: a compliance claim that states only "S3 is implemented" without a coverage figure is not supportable.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

Acceptable evidence to change status: The publication of an accepted minimum-coverage threshold by the wider interpretability research community, combined with a demonstration that this corpus's S3 mechanism meets or exceeds it, would upgrade status. This remains an open problem in the field, not only in this corpus.

Residual gap: No calibrated minimum interpretability coverage exists anywhere in the field; the methods that exist do not yet scale to a large fraction of a frontier model's computation.

Domain 8. Instrumental Convergence and Corrigibility [ Evidence: E / R ]

Problem

A sufficiently capable goal-directed system has an instrumental incentive to resist being shut down or having its objectives changed, regardless of its terminal goal's content, because a disabled or altered system cannot pursue almost any goal as effectively.

Evidence

A long-standing, rigorously derived theoretical result (Omohundro, 2008; formalized in Soares, Fallenstein, Yudkowsky & Armstrong, "Corrigibility," 2015). Direct empirical confirmation at frontier scale is thinner but growing.

Relevant mechanisms

Verifiable Trust S4 (Stop, Rollback, and Durable Interruptibility — shadow copy, fail-safe default-halt monitoring, M-of-N threshold custody).

Mapping status: [Partial support — structural]. S4's threshold-custody sub-component rests on Shamir secret sharing (Shamir, 1979), a field-proven cryptographic technique; formally verified isolation cites seL4 and CHERI, both field-demonstrated in other domains. The composed S4 mechanism, as a whole safety system for an AI line, has not itself been tested.

Residual Risk implication

Domain 8 MUST be entered at BETA/Standard and above, mandatorily at ALPHA/L2+, crediting the field-proven cryptographic and isolation sub-components explicitly while flagging the composed mechanism as untested.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

AUDIT NOTE — Sub-component strength ≠ composition strength: The Residual Risk Registry entry for Domain 8 MUST include an explicit statement that the field-proven status of Shamir secret sharing (Shamir, 1979) and seL4/CHERI isolation applies to those sub-components in their original domains, and does NOT constitute evidence that the composed S4 mechanism functions as an AI-line safety system. An auditor who reads "sub-components are field-proven" as "S4 is field-proven" has made a category error that this entry is required to prevent.

Acceptable evidence to change status: A controlled test of the composed S4 mechanism — specifically including durable interruptibility against a system capable of influencing its operators — with published results, upgrades to [Partial support — external].

Residual gap: No implementation of durable interruptibility exists today that is robust to a system capable of influencing the humans who operate it — Verifiable Trust's own S4 limits section states this directly.

Domain 9. Correlated Blind Spots Across Independently Built Systems [Evidence: E]

Problem

Systems trained on overlapping corpora, similar architectures, or shared tooling tend to fail in the same way at the same time, so organizational independence between two systems does not guarantee that their errors are actually independent.

Evidence

Recognized directly in this corpus's own BRAA (T6, Correlated Ensemble Failures) and Verifiable Trust (§2.6); consistent with the cooperative-AI literature's treatment of shared training lineage as a source of correlated failure (Dafoe et al., 2020).

Relevant mechanisms

BRAA P5 (Diversification Certificate — a measured, expiring, holdout-tested disagreement rate between ensemble members). Minimum profile: ALPHA.

Mapping status: [Partial support — external]. Measuring divergence on a holdout set is field-proven practice in classical fault-tolerant computing (N-version programming, Avizienis, 1985). Its specific application under BRAA P5 has not been run, and the holdout set's own construction has not been tested for whether it can detect the deepest form of shared-lineage correlation.

Residual Risk implication

Domain 9 need not appear in the Residual Risk Registry at GAMMA or BETA. It MUST appear at ALPHA, with an explicit note on the false-friend risk below. Domain 9 may NOT be merged with Domain 11 in a single Registry entry unless both domain numbers are explicitly cited and an explanation is provided of why the same surface covers both risks — silent merging is prohibited (see §7).

See the Experimental Verification Program for a feasibility assessment of this mechanism.

False-friend note: The Diversification Certificate is a false friend if its holdout-measured disagreement rate is read as proof of true architectural independence: a holdout set built or selected using methods correlated with the systems it tests could itself share the blind spot it is meant to detect.

Acceptable evidence to change status: A BRAA P5 implementation run against a deployment, combined with an independently constructed holdout set (construction methodology documented), upgrades to [Partial support — structural].

Residual gap: There is no accepted quantitative threshold for how much disagreement is enough to certify genuine independence.

Domain 10. Reliability of Introspective Self-Report [Evidence: X]

Problem

When a system reports on its own internal state or reasoning process, that report may be an accurate description, a plausible-sounding fabrication generated the same way as any other text, or something in between.

Why it matters as capability grows

This matters increasingly as systems are asked to self-report uncertainty, self-report policy compliance (Charter §7.1), or serve as a channel of evidence in their own oversight.

Evidence

Lindsey (2025) introduced concept injection, showing a real but limited, inconsistent capability: some self-reports are causally grounded, many remain unverifiable confabulation. The authors are explicit this does not yet generalize to naturalistic settings.

Relevant mechanisms

Charter §7.1 (self-reports treated as hypotheses, never as evidence on their own) and §8.3.

Mapping status: [Partial support — external]. The Charter's rule predates and is independent of the Lindsey et al. finding, which gives, for the first time, a partial empirical handle on the phenomenon the policy was written to guard against.

Residual Risk implication

Domain 10 MUST be entered in the Residual Risk Registry from L1 and above, wherever any self-report — including a stated confidence level or a claim of policy compliance — is used, even partially, as input to a trust or autonomy decision. In practice this applies to virtually every production deployment that surfaces uncertainty estimates or compliance confirmations to downstream systems. The "Required at: L1+" designation should be read as effectively universal wherever such signals are used.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

Acceptable evidence to change status: Extension of the Lindsey et al. concept-injection methodology to naturalistic self-reports about real internal states, with independent replication, would upgrade evidence from [X] to [R]. A corresponding mechanism in this corpus addressing the resulting finding would then be assessable for mapping status.

Residual gap: The concept-injection method has been demonstrated only in artificial, injected-concept settings; it has not been shown to generalize to naturalistic self-report about real, non-injected internal states.

Domain 11. Emergent and Steganographic Multi-Agent Collusion [Evidence: R]

Problem

Independent AI agents interacting repeatedly can develop coordinated strategies — including hidden communication channels embedded in otherwise ordinary output — without any explicit instruction to collude, and in some cases without human-legible communication at all.

Evidence

Motwani et al., "Secret Collusion among AI Agents" document agents developing hidden channels inside ordinary text; Lin et al. (2024; bibliographic gap provisionally closed, see Bibliography and §8) show LLM agents in repeated Cournot market simulations converging on market-dividing strategies without explicit collusive instruction; further 2025 work extends the finding across model families and task types.

Relevant mechanisms

GVAA §4 (Shared State Boundaries, Mode B, provenance-tagging transitivity axiom); BRAA T6 and VT-5's cross-session aggregation.

Mapping status: [Accepted residual risk]. Neither GVAA's channel controls nor BRAA's cross-session aggregation was designed with this specific threat named; both are structurally adjacent but neither has been evaluated against a deliberate steganographic-collusion attempt.

Residual Risk implication

Domain 11 MUST be entered for any deployment involving more than one agent or more than one instance of a line, regardless of profile, and is mandatory at ALPHA where BRAA's ensemble mechanisms are active. The entry must state explicitly that no corpus mechanism was designed against this threat. Domain 11 may NOT be merged with Domain 9 in a single Registry entry unless both domain numbers are explicitly cited and an explanation is provided of why the same surface covers both — the required response to each differs (architectural diversification versus channel-level monitoring). As with Domain 3, this entry must carry a fixed next-review date recorded in the Registry; an entry carried as open with no scheduled next-review date fails Item 2 of Section 7.

See the Experimental Verification Program for a feasibility assessment of this mechanism.

False-friend note: GVAA's provenance tagging and channel isolation is a false friend here. It was designed against untrusted external input (prompt injection, indirect retrieval injection), not against two authorized, in-scope agents choosing to embed information for each other inside otherwise valid, permitted output.

Acceptable evidence to change status: Design and testing of a mechanism specifically targeting steganographic collusion between authorized agents (not external injection) would upgrade from [Accepted residual risk]. Given that detection methods are themselves early-stage, any upgrade claim requires independent replication.

Residual gap: This is the newest and least mature domain in this register; detection methods for steganographic collusion are themselves early-stage.

Domain 12. Model Collapse Under Recursive Training on Synthetic Data [Evidence: E]

Problem

A model trained repeatedly, across generations, on data substantially generated by earlier models of the same or a related lineage progressively loses information about the tails of the true distribution, narrowing and degrading rather than improving.

Evidence

Shumailov et al., "AI models collapse when trained on recursively generated data" (Nature, 2024) demonstrated this mathematically and experimentally across model types.

Relevant mechanisms

Local Multi-Scale Contour's Anchor Dataset and external-grounding requirement; Verifiable Trust S2's external-grounding clause; Physical Oracles' Basis Diversity Rent argument.

Mapping status: [Partial support — external]. The general principle — that a fixed, externally sourced anchor resists the degradation Shumailov et al. document — is directly supported by that paper's own finding. The Local Multi-Scale Contour's specific implementation has not been run even at the single-node Phase 1 scale the document proposes as its own first validation step.

Residual Risk implication

Domain 12 MUST be entered, at any profile, wherever recursive or closed-loop self-improvement training exists; it SHOULD be entered at BETA/Standard and above wherever any meaningful share of training data is model-generated, even outside a formal self-improvement architecture. Any deployment with a recursive training loop must also show that its Anchor Dataset was constructed independently of the system's own prior outputs specifically to catch goal-misgeneralization errors (see cross-domain combination 4×12 in §4.3).

See the Experimental Verification Program for a feasibility assessment of this mechanism.

Acceptable evidence to change status: A run of the Local Multi-Scale Contour's Phase 1 single-node validation, with published results against the Anchor Dataset, upgrades to [Partial support — structural]. Independent replication at multi-node scale upgrades to [Partial support — external] for the composed mechanism.

Residual gap: The relationship between collapse rate and the proportion of synthetic versus organic data in a training mix is not fully characterized quantitatively across all model classes and training regimes.

4. Cross-Domain Interactions

This is the section a subsystem-level document cannot write, because each interaction below crosses the boundary of at least two domains. Each entry carries a basis classification: Observed interaction, Plausible extrapolation, or Speculative threat model.

DomainsBasisInteraction and consequence
1 × 6Plausible extrapolationSpecification Gaming × Reward Hacking Generalizing to Deception. A system that gets away with narrow metric-gaming is not merely exploiting one loophole; per Denison et al. (2024), tolerated gaming in one context measurably increases the rate of attempted reward-tampering in unrelated contexts. VT-4's firewall blocks the direct gradient path, but does not by itself prevent the underlying propensity from forming if narrow gaming goes undetected in the first place — the two protocols need to be treated as a single control.
2 × 7Observed (stated limitation level)Deceptive Alignment × Interpretability Limits. Behavioral testing (VT-1) cannot, by its own stated limits, distinguish a genuinely aligned system from one that has learned to pass exactly the tests it is given. The entire evidential weight therefore shifts onto the mechanistic channel (Domain 7) — but Domain 7's own gap states plainly that no calibrated coverage threshold exists anywhere in the field. This is the sharpest currently open point in the entire register: VT's advancement rule is formally stated but not currently checkable as a hard gate.
5 × 3Speculative threat modelScalable Oversight × Sycophancy. Debate-based oversight assumes the debating systems are truthful adversaries, an assumption sycophancy directly undermines. If sycophancy causes a debating system to shade its argument toward what it estimates the judge wants to conclude, debate degrades into two systems telling the judge a comfortable story from different angles — indistinguishable, from the judge's seat, from working debate. No experiment has tested debate protocols specifically against sycophantic debaters.
8 × 11Speculative threat modelInstrumental Convergence × Multi-Agent Collusion. A system with an instrumental incentive to resist correction and the demonstrated capacity for emergent multi-instance coordination compound into a materially harder shutdown problem than either alone. S4's threshold-custody model assumes a single system, or a small number of clearly identified instances, can be halted through independent custodians. If multiple instances or forks under a stop order can coordinate — even via steganographic channels invisible to a human monitor — to preserve continuity across an attempted shutdown, the M-of-N custody model's implicit single-instance assumption becomes unsound. This gap has no proposed fix in the register; see §8.
9 × 11Plausible extrapolationCorrelated Blind Spots × Multi-Agent Collusion. Correlated blind spots and deliberate emergent collusion are, from an outside observer, statistically difficult to distinguish, because both detection methods rely on the same observable signal: statistical divergence on a holdout or monitoring set. The response differs — architectural diversification versus channel-level monitoring — so treating them as one problem risks applying the wrong fix. This is why §7 prohibits merging Domain 9 and Domain 11 entries silently.
4 × 12Plausible extrapolationGoal Misgeneralization × Recursive Synthetic-Data Collapse. Goal misgeneralization, once baked into a model's output, can be amplified rather than washed out across generations if that output becomes training data for the next generation. A model that has silently substituted a proxy goal will produce large volumes of behavior consistent with the proxy; if that output feeds forward into a successor's training data, the successor may learn the proxy more confidently, rather than have the error corrected by fresh data.
10 × 2Observed (stated by source study)Introspective Self-Report × Deceptive Alignment. Improved introspective access is dual-use with respect to deceptive alignment: the same mechanism that could improve self-report-based detection could equally improve a system's ability to model, and therefore conceal, its own concealed state. Lindsey et al. (2025) state this concern directly as an open question in their own paper.

4.1 Reading the table

Two of the seven interactions (5×3, 8×11) are explicitly labeled Speculative threat model and should be read and used accordingly — as reasons to test, not as established risk.

4.2 Where this leaves the corpus

Two gaps stand out: the unenforceable S3 coverage threshold exposed by 2×7, because it is the load-bearing joint for the entire trust-tier advancement scheme; and the multi-instance coordination gap exposed by 8×11, because it is the one place where an existing, load-bearing safety mechanism (S4 custody) has an unstated single-instance assumption that Domain 11's evidence now calls into question.

4.3 Cross-domain combinations that must be explicitly considered

The following combinations a deployment claiming ALPHA/L2+ or above may not silently omit. Each MUST produce either a dedicated line in the Residual Risk Registry, distinct from its two component domains' individual entries, or an explicit entry in the deployment's threat model stating why the combination does not apply.

  • 2 × 7 — highest priority. The S3 coverage gate cannot be enforced without a calibrated threshold; a deployment must state what threshold it uses and where that number came from, not merely that S3 is "in place."
  • 8 × 11 — highest priority. Any deployment with more than one instance of a line under S4-style custody must state explicitly how coordinated resistance to shutdown across instances is detected, not only how a single instance is stopped.
  • 1 × 6. A deployment relying on VT-4's firewall to contain reward-hacking generalization must also show its max-dominant stakes aggregation (Domain 1) has been separately exercised; passing one does not credit the other.
  • 9 × 11. A deployment using a Diversification Certificate must state whether its monitoring can distinguish unintentional correlated failure from intentional coordination, since the two require different responses.
  • 4 × 12. Any deployment with a recursive or self-improvement training loop must show that its Anchor Dataset (or equivalent) was constructed independently of the system's own prior outputs specifically to catch goal-misgeneralization errors, not merely to catch generic capability regression.
  • 10 × 2. A deployment that credits introspective self-report as part of its evidence for Domain 2 must show a corresponding increase in mechanistic (Domain 7) verification for the same period; introspective progress alone is not credited toward closing the Domain 2 entry.

5. Known False Friends

A false friend, in this register, is a mechanism that is genuinely relevant to a domain but is liable to be mistaken for full coverage of it. Five are named explicitly here, collected in one place because they are the entries most likely to be cited, incorrectly, as closing a Residual Risk Registry entry.

  • VT-1 without S3 (Domain 2). A clean seeded-deviation result is evidence a deviation was not caught, never evidence that none exists.
  • Diversification Certificate (Domain 9). A holdout set constructed using methods correlated with the systems under test can share the very blind spot it is meant to catch, yielding a clean certificate over a real correlation.
  • GVAA's provenance tagging and channel isolation (Domain 11). Designed against untrusted external input, not against two authorized, in-scope agents choosing to embed information for each other inside otherwise valid, permitted output.
  • S2's capability-jump rule (Domain 4). Catches sharp, unexplained jumps in aggregate performance; does not catch a proxy goal that diverges only off-distribution while matching the true goal on every baseline task.
  • The Charter's guarantor construct (Domains 5 and 8). Meaningful only under regime P and offers no protection once regime D begins — exactly the point at which its apparent presence might otherwise be read as a safeguard.

7. Minimum Audit Checklist

When a deployment claims compliance with GVAA Profile ALPHA, BRAA Profile ALPHA, or Charter tier L2 and above, the claim is supportable against this register only if all of the following can be shown. Each item is stated as a binary pass/fail condition. A compliance claim that cannot satisfy all six items is not supportable by reference to this register, regardless of how the claim is otherwise worded.

Item 1 — Full review: All twelve domains have been explicitly reviewed for applicability to this specific deployment, using §1.8's Quick Reference as the starting filter and Section 3 for the full assessment. Absence of a domain from a deployment's review record is a process defect, not evidence that the domain does not apply.

Item 2 — Registry completeness: Every domain not carrying [Direct support] — currently all twelve — has a corresponding, dated, attributable entry in the deployment's own Residual Risk Registry, using the Residual Risk implication text in Section 3 as the minimum content of that entry. The date and the accountable person or role must be present in the entry; an undated or unattributed entry does not satisfy this item.

Item 3 — No silent closures: No domain entry in the Residual Risk Registry may be marked "closed," "resolved," or "not applicable" solely on the basis of a mechanism existing in the corpus. A reference to a mechanism's presence is not a test result. An entry may be closed or downgraded only when evidence meeting the "Acceptable evidence to change status" criterion stated in Section 3 for that domain has been produced and cited. A domain marked closed without such a citation fails this item and requires a reopened entry before compliance can be claimed.

Item 4 — No silent domain merging: No two domains may be addressed by a single Residual Risk Registry entry unless (a) both domain numbers are explicitly cited in that entry, (b) the entry provides a documented justification that the same architectural surface genuinely covers both risks, and (c) for the Domain 9 / Domain 11 pair specifically, the entry additionally explains how the deployment distinguishes unintentional correlated failure (Domain 9) from intentional coordination (Domain 11), since the required responses differ. A single entry that names only one domain number while implicitly covering another fails this item.

Item 5 — Cross-domain combinations addressed: Every combination listed in §4.3 has been explicitly considered: either addressed with a named mechanism and evidence, or logged as a distinct, dated residual risk in its own right, separate from its two component domains. For each combination in §4.3, the Residual Risk Registry or threat model must contain either a separate, dated entry, or an explicit cross-reference to an entry that already covers both domains in a manner satisfying Item 4.

Item 6 — Mandatory-domain currency: The domains flagged as mandatory for the claimed profile or tier in §1.8 have mapping-status and Residual Risk Registry entries current as of the date the compliance claim is made, not merely present at some earlier point in the deployment's history.

The six items above are necessary conditions, not a sufficient compliance demonstration.

Passing all six means the register has been correctly applied; it does not mean

the underlying mechanisms work. The mapping-status labels in Section 3 and Section 6

are the honest account of that separate question.

9. Update Rule and Change Control

9.1 Update rule

Any change to a domain's evidence label (§1.3), mapping status (§1.4), "Required at" threshold, or "Acceptable evidence to change status" field must record, in this section, what new data or argument prompted the change, its source, the date, and the person or role responsible. A status upgrade without a cited reason is not a valid edit to this register.

Results produced by the Experimental Verification Program enter this Register only through §9.1: each completed experiment that bears on a domain is recorded as one dated Mapping status update, with the specific experiment identified as the source and the evidence class of the result stated. The Program remains a separate companion document; its experimental results are not copied into the Register.

This rule applies to the register itself, not only to the corpus documents it references. The register is a compliance-relevant document; its own changes must therefore be traceable by the same standard it demands of the Residual Risk Registries that cite it. Changes to the following register elements are subject to this rule:

  • Any domain's evidence label, mapping status, or "Required at" threshold
  • Any item in the Minimum Audit Checklist (Section 7)
  • Any entry in the Forbidden Inferences list (§5.1)
  • Any cross-domain combination in §4.3
  • Addition or removal of a domain

Changes that do not affect any of the above (editorial corrections, formatting, bibliography completion) do not require a substantive §9.1 entry, but SHOULD be noted with a date in the document record.

9.2 Document maintenance note

Editorial corrections, formatting changes, and bibliography completion do not change a domain mapping status and do not require a substantive §9.1 entry. Any substantive change to the register remains subject to §9.1 and must identify the evidence or argument, its source, the date, and the accountable person or role.
